# 비밀번호 복구·계정 잠금 해제 (#14)

## 화면과 메일 링크

| 화면 | 프론트 경로 |
| --- | --- |
| 비밀번호 재설정 메일 요청 | `/password/forgot` |
| 비밀번호 재설정 | `/password/reset?token=...` |
| 계정 잠금 해제 메일 요청 | `/account/unlock-request` |
| 계정 잠금 해제 | `/account/unlock?token=...` |

메일 링크 주소는 아직 미정이므로 위 경로를 프론트 기준으로 제안한다.
배포 전 백엔드 메일 템플릿의 프론트 호스트·경로·쿼리 키 `token`을 이 경로에 맞춰야 한다.
토큰이 없거나 `token` 쿼리가 여러 개면 잘못된 링크로 안내한다.
토큰이 바뀐 링크로 이동하면 입력과 오류 상태를 새로 시작한다.

로그인 화면의 비밀번호 찾기와 계정 잠김 안내에서 각각 요청 화면으로 이동한다.
메일 링크 화면은 `(guest)` 가드를 적용하지 않아 로그인 중에도 열 수 있다.
화면 진입·메일 미리보기만으로 일회용 링크를 소비하지 않고 사용자의 버튼 클릭 후 요청한다.
복구 화면은 검색 색인을 제외하고 referrer를 보내지 않는다. 토큰은 저장소나 로그에 기록하지 않는다.

## API와 상태

- 요청: `POST /api/auth/password/reset-request`, `{ email }`
- 재설정: `POST /api/auth/password/reset`, `{ token, newPassword, newPasswordConfirm }`
- 요청: `POST /api/auth/account/unlock-request`, `{ email }`
- 해제: `POST /api/auth/account/unlock`, `{ token }`

모두 `auth: false`이며 로그인 토큰을 첨부하거나 재발급하지 않는다.
메일 요청 성공은 실제 발송 보장이 아니다. 가입 여부·소셜 전용 계정·서버의 발송 제한과 관계없이 같은 안내를 보여준다.
메일 링크의 유효 시간은 서버 기준 15분이다. 프론트는 링크 발급 시각을 추측해 타이머를 만들지 않는다.
비밀번호는 8자 이상 영문·숫자·특수문자, UTF-8 72바이트 이하, 확인값 일치를 검사한다.

- `AUTH_008`, `COMMON_002`: 입력 수정 후 같은 링크로 재시도 가능
- `AUTH_011`: 잘못된 링크·만료·사용 완료 → 새 메일 요청
- `AUTH_028`: 기존 비밀번호와 같음. 링크가 소모되었으므로 새 메일 요청
- `AUTH_002`: 계정 없음 → 로그인 또는 메일 요청 화면으로 안내
- 네트워크·서버 오류: 오류 표시 및 재시도 제공. 서버에서 이미 처리됐다면 다음 요청이 `AUTH_011`일 수 있어 새 메일 요청 경로도 제공

재설정·잠금 해제 성공 후 이 기기의 토큰과 AuthProvider 로그인 상태를 지우고 로그인 버튼으로 전체 페이지 이동한다.
자동 로그인하지 않는다. 다른 기기·탭에서 기존 access token이 `AUTH_027`로 거절되면 재발급 없이 세션을 종료한다.

## 검증과 남은 확인

core 테스트는 `packages/core/tests/accountRecovery.test.ts`에 있다.
복구 API 테스트 10개와 별도 검증 환경의 DOM 화면 테스트 7개로 요청 중 중복 클릭, 재시도, 링크 소모 오류, 로그인 화면의 진입 경로를 확인했다.
DOM 테스트는 Next.js 탐색과 API를 모의 처리했으며 실제 브라우저·메일을 통한 검증을 대신하지 않는다.
실제 이메일 발송·비밀번호 변경·계정 해제 요청은 자동 테스트에서 실행하지 않는다.
Figma 도구 호출 한도로 디자인을 읽지 못해 기존 입력칸·버튼을 사용한 기능 구현이다. 시각 디자인 일치 검증은 추후 진행한다.
배포 전 실제 메일 링크의 경로와 토큰 전달, 15분 만료, 두 번째 사용 거절, 모든 기기의 세션 종료를 백엔드와 함께 확인해야 한다.
